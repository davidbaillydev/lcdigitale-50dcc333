- Payment providers are configured per restaurant in `restaurant_payment_providers` (service-role only, no RLS policies); keys are written by manager-checked server functions and only returned masked. Kiosk card payments go through the restaurant's SumUp reader via public server functions keyed by the unguessable order id. Why: per-restaurant merchant accounts without exposing secrets to browsers.
- Website online payments use each restaurant's own Stripe keys (stored in restaurant_payment_providers) with a PaymentIntent + Payment Element; online orders are inserted as `awaiting_payment` (hidden from the kitchen) and only become `new`/`accepted` after the server re-checks the PaymentIntent with Stripe. Why: the kitchen never sees unpaid orders and the browser is never trusted to confirm payment.
- PayPal (Orders v2 redirect + server capture) and Lyra/PayZen (signed V2 form, HMAC verified on return and via /api/public/lyra-ipn) are per-restaurant online providers; orders.payment_ref is prefixed paypal:/lyra: (Stripe = pi_). Why: one awaiting_payment flow, provider resolved server-side.
